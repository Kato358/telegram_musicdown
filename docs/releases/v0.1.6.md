# v0.1.6 worker 死掉自动补位；DB 写锁不再一抢就炸；构建上下文不再拖 950MB

对长期运行做了一轮稳定性审查，六处问题都落在「不是会不会坏，而是坏了没人知道」上：worker 静默死亡、SQLite 一忙就 `database is locked`、反代切断 SSE 后只能靠退避重连、每条日志一次 open/close、以及 Docker 每次构建都把宿主机 946MB 的曲库和整个 `data/` 目录打包上传。

- **下载 worker 死亡自动补位**：`start_workers` 原先裸 `create_task`，而 worker 的「失败记账」路径（`_fail_or_retry` 自身抛错，如 DB 故障）会让异常逃出 `_worker`——worker 静默退出，并发池悄悄少几个人，下载页看起来「不动了」却没有任何报错。现在 done-callback 记录并以同编号 worker 补位；停机期抑制重生，`stop_workers` 二次扫取消防孤儿
- **死掉的 worker 名下任务不再僵死**：`next_queued_task` 取到任务即标 `downloading`；记账失败致 worker 死亡时若不放回 `queued`，补位的 worker 只会查到一条 `downloading`——任务僵在队列里直到下次重启才被 `recover_interrupted` 收走
- **入队即时唤醒 worker**：空转不再 0.5s/worker 常驻轮询 SQLite。入队/恢复/重试都 `set()` 事件；`IDLE_POLL_SEC=2s` 兜底只服务「退避时间到了」这类由时间驱动的就绪
- **SQLite 多连接从隐患变成设计用法**：连接改为**按线程独立**（`threading.local`）——store 的写路径 `with self._conn:` 是多语句事务，事件循环线程与 `to_thread` 工作线程此前共用一条连接，两个线程的语句会落进同一事务，一边回滚另一边跟着遭殃；WAL 下多连接读写不互斥。同时补上 **`PRAGMA busy_timeout=5000`**：此前完全没有，任何第二连接（备份工具、迁移连接）抢不到写锁立刻 `SQLITE_BUSY`
- **迁移事务化**：每个迁移文件与其 `schema_version` 记档包在同一个 `BEGIN IMMEDIATE…COMMIT` 里（`executescript` 会隐式提交挂起事务，边界只能写进脚本文本），崩在中间不再留下「文件应用了、版本没记」的中间态；并发启动由写锁排队
- **SSE 空闲心跳**：`/api/events` 在安静期（无下载进行时）此前完全没有字节输出，nginx 等反代按默认 60s 切断，浏览器只能靠 EventSource 退避重连恢复。现在空闲 15s 发 `: ping` 注释帧，EventSource 忽略它
- **日志句柄常开**：原先每条记录 `open("a")`+写+关，高频 INFO（连接类事件）下是纯 SysCall 浪费。Windows 上还有个暗坑：裁剪时**开着的追加句柄会让同目录 `replace` 占用失败**，裁剪会静默全败、文件无限增长——现改为先收句柄再重写
- **构建上下文瘦身**：新增 `.dockerignore`——`downloads/`（实测 946MB）、`data/`、各类缓存、`web/dist`（本就容器内构建）不再进 context，每条 push 的 CI 都少传约 1GB
- **部署与工程整洁**：Dockerfile `useradd` 固定 UID 1000（宿主挂载授权不再每次重建都变）；`pyproject` version 对齐 release（0.1.5）；pytest `filterwarnings` 消掉 proactor `ResourceWarning` 测试噪音（对象分配自 Kurigram 测试桩的事件循环，非业务泄漏）；`run.py` 绑 `0.0.0.0` 时若用的是默认口令 `123`，启动即告警
- **零碎**：ChKSz 下载分块 64KB→256KB（>100MB 母带的迭代次数降到 1/4）；`preview` 淘汰 docstring 与实现口径对齐（试听以表为准、封面按磁盘实测，原文写反了）

## 验证与已知残留

`ruff` 全绿、`mypy --strict`（79 files）无错、`pytest` **429 例全过**（较 0.1.5 的 417 例新增 12 个回归：worker 死亡补位、停机抑制重生、入队唤醒时延、SSE 心跳/事件帧/断开摘订阅、按线程连接、busy_timeout、迁移幂等、close 收口全部连接、logfile 裁剪后句柄仍写）。

真实应用冒烟（现网 `data/app.db` 副本 + 现网会话）：迁移在旧库上无重放、3 个 worker 正常起池、`/` 200、`/api/events` 200 `text/event-stream` 且 **17 秒后实测收到 `: ping` 帧**、日志经新句柄正常写入。

**已知残留（同 0.1.5 记录，上游问题本仓库不修）**：Kurigram 的 `TCP.close()` 不关 `CryptoWorker` 线程池、`Client.terminate()` 不关 `Client.executor`——每次会话重连与每次重建 Client 各漏若干线程。判断：`docker exec musicdown sh -c 'grep Threads /proc/1/status'`。

## 镜像

```bash
docker pull ghcr.io/kato358/telegram_musicdown:0.1.6
docker pull ghcr.io/kato358/telegram_musicdown:0.1
```

`:latest` 仍跟着 `main`；`:0.1` 随本条移动到 0.1.6。要锁版本就把 compose 里的 `image:` 钉到 `:0.1.6`。
